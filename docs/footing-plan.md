# 기준서 footing 계획 (v1 · 2026-09-08 확정)

> 검수 마감 **9/11(목) 18시** · v0 확정 **9/15(월)** · 검수자 4명 · **1인 약 6시간**
> 작업 공간: Notion `기준서 footing 검수` DB / 코드·데이터: GitHub

## 왜 이렇게 하는가

40개 기준서 3,661문단을 4명이 전수로 원문 대조하면 1인 900문단이다. 9/15까지 끝날 일이
아니고, 끝나도 무엇을 어디까지 봤는지 남지 않는다.

그래서 순서를 바꾼다. **기계가 잡을 수 있는 결함을 전수로 먼저 걸러내고, 사람은 두 가지만
본다 — 기계가 짚었지만 판정할 수 없는 지점(233곳), 그리고 기계가 놓쳤을 수 있는지 보는
표본(200문단).** 합쳐서 433건, 전체 문단의 11.8%다.

## 1단계 — 자동 1차 검증 (완료)

```bash
python3 scripts/audit_standards.py --assign 4 --worksheet 기준서_footing_검수.csv
```

| 규칙 | 심각도 | 건수 | 무엇을 의심하는가 | 건당 |
| --- | --- | ---: | --- | ---: |
| `NUM_GAP` | P1 | 6개 기준서 | 본문 문단번호가 중간에 비어 있음 | 10분 + 누락 10개당 5분 |
| `HEADING_LEAK` | P2 | 208 | 마지막 줄이 본문이 아니라 다음 절의 제목으로 보임 | 2분 |
| `OVERSIZE` | P2 | 18 | 2,500자 초과 — 여러 문단이 하나로 붙었을 가능성 | 6분 |
| `TAIL_NOISE` | P2 | 1 | 마지막 줄이 쪽번호 등 본문이 아닌 흔적 | 2분 |
| `SAMPLE` | 표본 | 200 | 자동검증에 걸리지 않은 문단 (기준서당 5개, 시드 고정) | 3분 |
| `SETUP` | 착수 | 40 | 원문을 열고 기준서 범위를 확인 | 5분 |

**합계 1,436분 = 23.9시간 → 1인 6.0시간.** 건당 시간은 실측이 아니라 계획용 가정이며,
1차 검수가 끝나면 실제 소요시간으로 갱신한다.

### 자동 검증이 이미 찾아낸 실제 결함

- **제1032호 문단 5·6·7 누락** — 문단 4 다음이 곧바로 8이다. 파서가 놓쳤다.
- **제1032호 문단 100 (10,238자)** — `[…삭제함]` 뒤에 부록 적용지침(AG1~) 전체가 한 문단으로
  딸려 붙었다. 이 상태로 조서에 담으면 200행이 쏟아진다.
- **제1116호 문단 2** — 본문 끝에 다음 절 제목 `적용` 이 붙어 있다.
- **제1007호 문단 52** — 끝줄이 `시행일고과 경과 규정` 으로, 제목이 깨진 채 섞였다.

반대로 `HEADING_LEAK` 208건에는 정상인 것도 섞여 있다. 그래서 사람이 본다.

## 2단계 — 사람 검수 (9/9 ~ 9/11)

### 배분 (`--assign 4`)

담당 기준서 수는 정확히 10건씩 맞추고, 예상시간이 큰 기준서부터 한가한 담당자에게 붙여
시간 편차를 줄였다.

| 검수자 | 기준서 (10건) | 확인지점 | 예상시간 |
| --- | --- | ---: | ---: |
| 1 | 1101, 1036, 1019, 1041, 1114, 1027, 1002, 1008, 1024, 1106 | 67곳 | 6.2h |
| 2 | 1039, 1113, 1116, 1103, 1021, 1037, 1007, 1028, 1010, 1026 | 52곳 | 5.9h |
| 3 | 1115, 1107, 1117, 1112, 1034, 1040, 1012, 1105, 1020, 1029 | 63곳 | 5.9h |
| 4 | 1032, 1102, 1001, 1110, 1033, 1108, 1016, 1111, 1023, 1038 | 51곳 | 5.9h |

각 검수자에게 표본 50문단(기준서당 5개)이 함께 배정된다. 표본은 시드 `20260908` 로 고정되어
누가 언제 다시 돌려도 같은 문단이 나온다.

### 판정 4가지

각 행의 `판정` 은 넷 중 하나다. **수정안을 쓰는 것이 아니라 판정만 하면 된다.**

| 판정 | 언제 |
| --- | --- |
| `정상` | 원문과 같다. 자동검증이 과하게 잡은 경우 |
| `오류` | 원문과 다르다. `수정내용` 에 무엇이 어떻게 달라야 하는지 한 줄 |
| `판본차이` | 내가 본 원문과는 다르지만, 판본이 달라서일 수 있음 |
| `판단보류` | 원문을 봐도 판단이 안 섬. 이유를 `비고` 에 한 줄 |

### 원문은 각자 편한 것으로 — 대신 출처를 남긴다

법인에 올라가 있는 기준서, 회계기준원 웹 공시본, 보유한 HWP 중 무엇을 봐도 된다.
**대신 `대조출처` 열에 무엇을 봤는지 적는다** (예: `법인 포털`, `기준원 웹`, `HWP 2023판`).

판본이 갈리면 판정도 갈린다. 그래서 `오류` 로 단정하기 애매하면 `판본차이` 로 두고 넘어간다.
`판본차이` 로 모인 행은 취합 후 한 판본으로 일괄 확인한다 — 검수자가 판본을 맞추려고
시간을 쓰지 않는 것이 이 규칙의 목적이다.

### 표본 문단은 이렇게 본다

`SAMPLE` 행은 자동검증에 안 걸린 문단이다. 원문과 나란히 놓고 **본문이 통째로 같은지,
문단번호가 맞는지, 앞뒤가 잘리지 않았는지** 세 가지만 본다. 문장 부호나 띄어쓰기 차이는
`정상` 으로 넘긴다.

## 3단계 — 수정과 재검증 (9/12)

1. `오류` 판정을 모아 **파서(`scripts/parse_kifrs_hwp.py`)를 고쳐 재파싱**하는 것이 원칙이다.
   JSON 직접 수정은 재파싱 때 되돌아가므로 최후 수단으로만 쓴다.
2. `판본차이` 는 한 판본으로 일괄 확인 후 `정상` 또는 `오류` 로 확정한다.
3. 재파싱 후 `audit_standards.py` 를 다시 돌려 P1이 0인지 확인하고, 확정된 오류 문단을
   직접 재확인한다.

## 배포 판정 기준 (9/15)

| 등급 | 기준 |
| --- | --- |
| 배포 가능 | P1 0건 · 확인지점 판정 100% · 표본 200문단에서 신규 결함 0건 |
| 조건부 배포 | P1 0건 · 미판정 20건 이하 (해당 기준서에 안내 배너 표시) |
| 배포 보류 | P1 잔존 또는 표본에서 신규 결함 발견 |

표본에서 신규 결함이 나오면 그 유형을 자동검증 규칙으로 추가하고 전수 재검출한다 —
표본을 두는 이유가 이것이다.
