# 기준서 footing — 발견한 사람이 그 자리에서 고친다

검수 워크시트를 돌리고 판정을 취합하는 대신, **앱에서 바로 고치고 고친 기록만 남긴다.**
쓰다가 이상한 문단을 만난 사람이 그 자리에서 고치는 것이 가장 빠르고, 기록이 남으므로
나중에 무엇이 왜 바뀌었는지 되짚을 수 있다.

## 흐름

```
어디를 볼지 안다 → 앱에서 고친다 → 수정 로그를 내보낸다 → 검토한다 → 원본에 반영한다
   audit_standards.py      수정 모드        .md / .json      edit-log.md    --apply
```

### 1. 어디를 볼지 (선택)

수정 모드 띠의 **`의심 문단 훑기`** 를 누르면 앱이 그 자리에서 전 기준서를 점검한다.

- 의심 문단은 본문에서 **노란색 음영**과 규칙 이름(`제목 유입 의심` 등)으로 표시된다
- 왼쪽 기준서 목록에는 기준서별 의심 지점 수가 배지로 붙는다
- `목록` 을 누르면 규칙별로 걸러 보고, 문단번호를 눌러 그 자리로 건너뛴다
- **고치면 표시가 사라진다** — 고친 내용을 다시 검사하기 때문이다

같은 점검을 터미널에서도 돌릴 수 있다.

```bash
python3 scripts/audit_standards.py
```

기계가 잡을 수 있는 결함 **230곳**(전체 문단의 6.3%)과, 어느 기준서에 몰려 있는지를 보여준다.
확인지점이 아예 없는 기준서도 10건 있다. 꼭 이 목록대로 볼 필요는 없다 — 쓰다가 이상하면
그때 고치면 된다.

| 규칙 | 심각도 | 건수 | 무엇을 의심하는가 |
| --- | --- | ---: | --- |
| `NUM_GAP` | P1 | 6개 기준서 | 본문 문단번호가 중간에 비어 있음 (앱에서 못 고침 — 파서 수정 필요) |
| `HEADING_LEAK` | P2 | 208 | 마지막 줄이 본문이 아니라 다음 절의 제목으로 보임 |
| `OVERSIZE` | P2 | 18 | 2,500자 초과 — 여러 문단이 하나로 붙었을 가능성 |
| `TAIL_NOISE` | P2 | 1 | 마지막 줄이 쪽번호 등 본문이 아닌 흔적 |

### 2. 앱에서 고친다

1. 상단 **`수정 모드`** 버튼 → 이름을 적고 시작. 이름은 브라우저에 기억된다.
2. 본문 문단마다 **`수정`** 버튼이 생긴다. 누르면 그 자리에서 본문과 문단제목(대분류·소분류)을
   고칠 수 있다. `왜 고쳤나요` 는 검토 문서에 그대로 실리므로 한 줄이라도 적는 편이 좋다.
3. `Ctrl/⌘ + Enter` 로 저장, `Esc` 로 취소. 고친 문단에는 **수정됨** 배지가 붙고,
   본문·검색·조서 미리보기에 모두 반영된다.
4. 잘못 고쳤으면 **되돌리기** 로 원본으로 돌아간다 (기록도 함께 지워진다).

**원본 JSON 은 앱에서 바뀌지 않는다.** 고친 내용은 브라우저(localStorage)에만 쌓이고,
내보낸 기록을 검토한 뒤에야 원본에 들어간다.

### 3. 수정 로그를 내보낸다

수정 모드 띠의 **`수정 로그`** → 두 가지를 내려받는다.

| 파일 | 쓰임 |
| --- | --- |
| `standards-edit-log-<시각>.md` | **검토용** — 수정 전/후 전문, 수정자, 사유가 들어 있다 |
| `standards-edit-log-<시각>.json` | **반영용** — 원본에 적용할 때 쓴다 |

둘 다 내려받아 함께 전달한다.

### 4. 검토하고 반영한다 (관리자)

```bash
# 여러 사람이 보낸 기록을 한 번에 — docs/edit-log.md 가 만들어진다
python3 scripts/apply_edit_log.py ~/Downloads/standards-edit-log-*.json

# 검토 문서를 보고 괜찮으면 반영
python3 scripts/apply_edit_log.py ~/Downloads/standards-edit-log-*.json --apply

# 반영 후 다시 검증
python3 scripts/audit_standards.py
```

`docs/edit-log.md` 에는 수정 전/후와 함께 **상태**가 붙는다.

| 상태 | 의미 | `--apply` 시 |
| --- | --- | --- |
| 반영 가능 | 원본이 기록의 '수정 전'과 같다 | 반영함 |
| 이미 반영됨 | 원본이 이미 '수정 후'와 같다 | 건너뜀 |
| 확인 필요 | 원본이 '수정 전'과 다르다 (다른 판본에서 고쳤을 수 있음) | 건너뜀 |
| 문단 없음 | 원본에 그 문단이 없다 | 건너뜀 |

같은 문단을 여러 사람이 고쳤으면 **마지막 수정만 반영하고, 덮인 기록을 문서에 남긴다.**
자동검증에 걸렸던 문단이면 어떤 규칙이었는지도 함께 표시되므로,
고친 내용이 그 결함을 실제로 해소하는지 바로 볼 수 있다.

## 이 방식으로 고칠 수 없는 것

- **문단 누락(`NUM_GAP`)** — 없는 문단은 앱에서 만들 수 없다. 파서
  (`scripts/parse_kifrs_hwp.py`)를 고쳐 재파싱해야 한다. 제1032호(5·6·7번 등 48개),
  제1039호(69개)가 여기 해당한다.
- **제1109호 '금융상품' 미반영** — 다단계 문단번호 대응 후 재파싱 필요.

## 남은 확인 사항

**기준서 원문의 사내 재배포 범위.** 회계기준원 저작물을 사내 도구에 담아 배포하는 것에
대한 법인 차원 확인이 배포 결정 전에 필요하다.
