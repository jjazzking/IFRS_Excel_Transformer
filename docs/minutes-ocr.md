# 스캔 페이지에 OCR 붙이기 — 설계

규칙 전용 PoC 는 전체 93% 에서 멈췄고, **틀린 것이 전부 스캔 페이지 하나에서 나왔다**
(`docs/minutes-plan.md` 3장). 이 문서는 그 한 곳을 메우는 설계다.

붙이기 전에 실제로 돌려 보고 썼다. 아래 숫자는 전부 이 저장소의 표본
(`sample-03-스캔혼재형.pdf`, 2쪽이 이미지)에서 잰 것이다.

---

## 0. 먼저 — 이건 항상 켜는 기능이 아니다

**스캔 페이지가 있을 때만 돈다.** 한글·워드에서 출력한 의사록은 텍스트 레이어가 이미 있고,
그런 페이지에 OCR 을 돌리면 돈과 정확도를 동시에 버린다. 페이지 판정은 이미 있다
(`minutes_text.py`, 글자 수 40 미만이면 이미지로 본다).

먼저 확인할 것은 엔진이 아니라 **비율**이다. 실제 의사록 20건을 규칙 전용으로 돌려
`SCAN_PAGE` 표시가 몇 건에 붙는지 세라. 0 이면 이 문서는 필요 없다.

---

## 1. 붙이는 자리 — 좌표계 하나만 지키면 된다

파이프라인은 이미 OCR 을 받을 모양으로 되어 있다. 갈아 끼울 자리는 ②단계 하나다.

```
① 페이지 분류 ─┬─ text ─→ PyMuPDF 낱말 ─┐
               │                        ├─→ ③ 좌표계 ─→ ④⑤⑥ 규칙·검증 (그대로)
               └─ scan ─→ OCR 낱말 ─────┘
```

두 경로가 **같은 모양**을 내놓으면 그 뒤는 한 줄도 바뀌지 않는다.

```python
class OcrWord(NamedTuple):
    text: str
    bbox: tuple[float, float, float, float]   # PDF 포인트, 페이지 좌표계
    line: int                                  # 줄 묶음 (본문에서 줄바꿈이 될 자리)
    confidence: float                          # 0~100

def ocr_page(page: pymupdf.Page, *, dpi: int = 150) -> list[OcrWord]: ...
```

`MinutesText(path, ocr=engine)` 로 엔진을 주입하고, 스캔 페이지에서만 `ocr_page` 를 부른다.
엔진을 안 주면 지금과 똑같이 돈다 — 스캔 페이지는 `SCAN_PAGE` 로 표시하고 넘어간다.

**좌표 변환은 여기서 끝낸다.** OCR 은 픽셀로 답한다. `점 = 픽셀 × 72 / dpi` 로 바꿔 넣으면
③ 이후는 텍스트 경로와 구분할 수 없다. 페이지를 돌려서 OCR 했다면 bbox 도 같이 되돌린다.
이 변환을 엔진 안에서 끝내지 않고 밖으로 흘리면, 근거 하이라이트가 페이지마다 어긋난다.

근거에는 `source: 'ocr'` 이 붙는다. 화면에서 다르게 보여야 하기 때문이다 — OCR 로 읽은
글자는 원문 그대로가 아니다.

## 2. 재본 결과

### 2-1. OCR 을 붙이면 놓쳤던 것이 돌아온다

`sample-03` 의 13개 필드 기준.

| | 맞은 필드 | 무엇이 달라졌나 |
| --- | ---: | --- |
| 규칙만 | 9/13 (69%) | 2쪽의 의안 하나와 폐회시각을 통째로 놓침 |
| 규칙 + OCR | 11/13 (85%) | 의안 경계·폐회시각 회복. **제목과 가결 여부는 여전히 틀림** |
| 규칙 + OCR + 공백 내성 | 13/13 (100%) | 4장의 규칙 손질까지 하면 |

가운데 줄이 이 문서의 핵심이다. **OCR 을 붙였는데도 두 필드가 틀렸다.** 엔진이 글자를 잘못
읽어서가 아니다. 4장에서 다룬다.

### 2-2. 해상도는 올릴수록 좋아지지 않는다

| dpi | 이미지 | 파일 | 렌더 | 본문 품질 |
| ---: | --- | ---: | ---: | --- |
| **150** | 1240×1755 | **36 KB** | 206 ms | **가장 깨끗** |
| 200 | 1653×2339 | 86 KB | 175 ms | 숫자 분절 시작 |
| 300 | 2480×3509 | 174 KB | 340 ms | 숫자가 더 잘게 쪼개짐 |

해상도를 올리면 글자 사이 간격이 벌어져 낱말이 더 잘게 쪼개진다. `5,000,000,000` 이
150dpi 에서는 `5, 000, 000, 000` 인데 300dpi 에서는 `5, 000, 0 00, 0 00` 이 된다.

**150dpi 를 기본값으로 둔다.** 파일이 작으므로 클라우드 OCR 에 보낼 때 업로드도 가볍다.
실제 스캔본(원본 해상도가 낮을 수 있다)에서는 다시 재야 한다.

### 2-3. 회전은 반드시 잡아야 하고, OSD 를 믿으면 안 된다

| 페이지 상태 | 평균 신뢰도 | 본문 |
| --- | ---: | --- |
| 정상 | 88.2 | 온전함 |
| 2도 기울어짐 | 90.5 | **온전함** — 약간의 기울기는 견딘다 |
| 90도 회전 | **43.0** | 완전히 깨짐 (`브 벼 [위 !으 콜 뜨…`) |

90도 회전된 페이지에서 Tesseract 의 방향 감지(OSD)는 **180도라고 답했다.** 틀렸다.
한국어 페이지에서 OSD 를 신뢰할 수 없다.

**대신 신뢰도로 판정한다.** 정상 88 대 회전 43 은 명확히 갈린다.

```
평균 신뢰도가 70 미만이면 → 90·180·270 도로 돌려 다시 OCR → 가장 높은 방향을 쓴다
한 페이지에서 방향이 정해지면 나머지 페이지는 같은 방향부터 시도한다
```

최악의 경우 페이지당 4회지만 **스캔 페이지에만, 그것도 신뢰도가 낮을 때만** 걸린다.
PDF 자체의 `/Rotate` 는 이미 렌더 단계에서 반영되므로, 여기서 잡는 건 스캐너가 종이를
돌려 넣은 경우다.

### 2-4. 낱말 신뢰도는 실제로 틀린 낱말을 가리켰다

| | 값 |
| --- | ---: |
| 낱말 수 | 68 |
| 평균 / 중앙값 | 88 / 93 |
| 하위 10% | 75 |
| 최저 | 24 |

**신뢰도 24 였던 두 낱말이 실제로 틀린 그 낱말이었다** (`000`, `원` — 금액이 깨진 자리).
모델이 스스로 매기는 신뢰도와 달리 OCR 엔진의 낱말 신뢰도는 근거가 있는 숫자다.
검증에 그대로 쓴다 (7장).

## 3. 어느 엔진을 쓸 것인가

| 후보 | 한국어 | 낱말 bbox·신뢰도 | 데이터 위치 | 비용 | 판단 |
| --- | --- | --- | --- | --- | --- |
| **Tesseract + `kor`** | 쓸 만함 (측정: 평균 88) | **있음** (TSV) | **로컬** | **0원**, 296 ms/쪽 | 1순위 — 밖으로 안 나간다 |
| Google Cloud Vision | 더 좋음 | 있음 | 국외 | 쪽당 수원대 | Tesseract 가 모자랄 때 |
| Naver CLOVA OCR | 최상급 (도장·표) | 있음 | **국내** | 건당, 더 비쌈 | 국외 이전이 막힐 때 |
| Upstage Document Parse | 한국어 문서 특화 | 있음 | 선택 | 쪽당 | 표가 많은 의사록에서 |
| PaddleOCR | Tesseract 보다 나음 | 있음 | 로컬 | GPU | Tesseract 가 모자랄 때의 로컬 대안 |

**Tesseract 로 시작한다.** 이유는 정확도가 아니라 경로다 — 파일이 밖으로 나가지 않으므로
보안 심의(`docs/minutes-plan.md` 벽 2)를 기다리지 않아도 되고, 293 KB 짜리 표본에서
이미 쓸 만한 결과가 나왔다. 클라우드 엔진은 `OcrWord` 를 내놓는 다른 구현일 뿐이라
언제든 갈아 끼운다.

성능이 모자라면 그때 비교하면 된다. 비교 방법은 이미 있다 — 같은 표본에
`eval_minutes.py` 를 엔진만 바꿔 두 번 돌린다.

## 4. 진짜 어려운 곳은 엔진이 아니라 낱말 분절

2-1 에서 OCR 을 붙였는데도 두 필드가 틀렸다. OCR 이 읽은 본문은 이랬다.

```
제 2 호 의안 ： 금 융 기관 차입 한도 약정 체 결 의 건
한도 금 액 은 금 5, 000, 000, 000 원 이다.
표결 결과 원 안 대로 가 결 하다.
```

글자는 **하나도 틀리지 않았다.** 공백이 들어갔을 뿐이다. 그런데 규칙은 이렇게 깨졌다.

| 필드 | 규칙 | 왜 깨졌나 |
| --- | --- | --- |
| 가결 여부 | `원안\s*대로\s*가결` | `원 안 대로` — `원안` 이 붙어 있지 않다. 한 단계 낮은 `가결` 로 떨어졌다 |
| 금액 | `[\d,]+\s*원` | `5, 000, 000, 000` — 숫자 사이의 공백을 넘지 못한다 |
| 의안제목 | 문자열 비교 | `금 융 기관…` 과 `금융기관…` 은 다른 문자열이다 |

반대로 **버틴 규칙들이 있다.**

| 필드 | 규칙 | 왜 버텼나 |
| --- | --- | --- |
| 폐회시각 | `_label("폐","회")` → `폐\s*회` | 글자 사이 공백을 이미 허용한다 |
| 의안번호 | `제\s*(\d+)\s*호\s*의\s*안` | 같다 |
| 시각 | `(\d{1,2})\s*시\s*(\d{1,2})?\s*분` | 같다 |

원래 `일    시` 처럼 **라벨을 벌려 쓰는 한국식 서식**을 견디려고 넣은 `\s*` 가, 그대로
OCR 의 낱말 분절을 견뎌 냈다. 규칙을 넓히는 방향이 이미 맞았던 것이다.

### 그래서 무엇을 고치는가 — 본문이 아니라 규칙을 고친다

공백을 지워서 해결하고 싶어지는데, **하면 안 된다.**

> ③ 좌표계는 **길이를 보존하는 정규화만** 허용한다. 본문에서 공백 하나를 지우면 그 뒤의
> 모든 오프셋이 한 칸씩 밀리고, 근거 좌표가 전부 어긋난다. 원문을 가리키는 설계
> (`docs/minutes-plan.md` 1장) 전체가 이 불변식 위에 서 있다.

대신 셋으로 나눠 푼다.

1. **정형구 패턴은 글자 사이에 `\s*` 를 넣는다.** `원안대로` → `원\s*안\s*대\s*로`.
   `_label()` 이 라벨에 하던 일을 결의 정형구·단위에도 적용한다. 손으로 쓰지 말고
   `_loose("원","안","대","로")` 같은 도우미로 만든다 — 규칙이 늘어날 때 빠뜨리지 않는다.
2. **숫자는 공백을 건너뛰게 한다.** `([\d][\d,\s]*[\d])` 로 받고 값으로 바꿀 때 공백과
   쉼표를 지운다. 줄바꿈은 넘지 않도록 `[ \t]` 로 제한한다.
3. **비교·표시할 때만 공백을 접는다.** 저장되는 값과 근거는 원문 그대로 두고, 정답 대조와
   화면 표시에서만 공백을 접어서 본다. `eval_minutes.py` 는 이미 공백을 접어 비교한다 —
   OCR 경로에서는 이 접기를 글자 사이까지 넓혀야 한다.

**1·2 는 텍스트 경로에도 해가 없다.** `\s*` 는 공백이 없을 때도 매치한다. 그래서 OCR 전용
규칙을 따로 두지 않는다 — 규칙은 하나로 유지하고 내성만 넓힌다.

## 5. 무엇을 새로 만들고 무엇을 고치는가

```
새로 만듦
  scripts/minutes_ocr.py       엔진 인터페이스 + Tesseract 구현 + 회전 판정
                               (클라우드 엔진은 같은 인터페이스의 다른 구현)

고침
  scripts/minutes_text.py      MinutesText(path, ocr=None) — 스캔 페이지에서만 엔진 호출
                               픽셀 → PDF 포인트 변환, Word 에 confidence 추가
  scripts/minutes_rules.py     4장의 1·2 — 정형구·숫자 패턴에 공백 내성
  scripts/parse_minutes.py     --ocr 플래그, 7장의 검증 규칙 둘 추가
  scripts/eval_minutes.py      공백 접기를 글자 사이까지
  scripts/requirements.txt     pytesseract (또는 subprocess 직접 호출)
  README.md                    설치 안내 (tesseract-ocr, tesseract-ocr-kor)
```

**기본값은 꺼짐이다.** `--ocr` 없이 돌리면 지금과 똑같이 동작한다. OCR 이 없는 환경에서
스크립트가 깨지지 않아야 하고, 스캔본을 다루지 않는 사람에게 설치를 강요할 이유도 없다.

## 6. 실행 순서

| | 하는 일 | 판단 |
| --- | --- | --- |
| 1 | 실제 의사록 20건을 규칙 전용으로 돌려 `SCAN_PAGE` 비율을 센다 | 0 이면 여기서 끝 |
| 2 | 4장의 규칙 내성부터 넓힌다 (OCR 없이) | 텍스트 경로 정확도가 떨어지지 않는지 확인 |
| 3 | Tesseract 를 붙이고 같은 표본을 다시 채점 | 규칙 전용 대비 올랐는가 |
| 4 | 안 오르면 엔진 비교, 그래도 안 되면 클라우드 | 여기서 처음 보안 심의가 필요해진다 |

**2 를 3 보다 먼저 한다.** 순서를 바꾸면 OCR 이 붙었는데 점수가 안 오르는 이유가 엔진
때문인지 규칙 때문인지 구분할 수 없다. 2-1 의 가운데 줄이 그걸 보여 준다.

## 7. 검증 규칙에 더할 것

신뢰도는 버리지 않고 검증에 쓴다 (`docs/minutes-plan.md` 5장의 표에 추가).

| 규칙 | 무엇을 확인 | 등급 |
| --- | --- | --- |
| `OCR_ORIENTATION` | 페이지 평균 신뢰도 < 70 — 회전·품질 의심. 네 방향 재시도 후에도 낮으면 표시 | P1 |
| `OCR_LOW_CONF` | 어떤 필드의 근거 구간에 걸친 낱말의 **최저** 신뢰도 < 60 | P1 |

평균이 아니라 최저를 보는 이유는 2-4 다. 평균 88 인 페이지 안에 신뢰도 24 짜리 낱말이
섞여 있었고, 틀린 건 그 낱말이었다. 금액·인원수처럼 **숫자 한 글자가 결과를 바꾸는 필드**
에서는 특히 그렇다.

`SCAN_PAGE` 는 의미가 바뀐다. 지금은 "읽지 못했다"이고, OCR 이 붙으면 "OCR 로 읽었으니
사람이 한 번 봐야 한다"가 된다. 등급은 P1 로 유지한다.

| | 건당 (10쪽 중 스캔 2쪽 가정) |
| --- | ---: |
| **Tesseract (로컬)** | **0원**, 0.6초 |

| 회전 재시도가 걸리면 | 위의 최대 4배 |

단가는 재확인할 것. **어느 쪽이든 비용은 제약이 아니다.** 클라우드로 갈 이유는 돈이 아니라
정확도이고, 그 대가는 돈이 아니라 보안 심의다.

| **오프셋 불변식 파괴** | 공백을 지우고 싶은 유혹 | 길이 보존 정규화만. 이 불변식이 깨지면 근거 추적 전체가 무너진다 |
| **회전 오판** | OSD 를 믿는 경우 | 2-3. 신뢰도로 판정한다 |
| **조용한 오독** | 신뢰도 낮은 낱말이 그럴듯한 글자로 읽힌 경우 | 7장. 최저 신뢰도로 필드를 내린다 |
| **날인·서명 페이지** | 본문이 거의 없는 쪽 | 애초에 뽑을 필드가 없다. `SCAN_PAGE` 만 남기고 넘어가도 된다 |

마지막 줄이 중요하다. **스캔 페이지라고 다 OCR 이 필요한 게 아니다.** 실무에서 스캔본인
페이지는 대개 날인·서명 장이고 거기엔 뽑을 필드가 없다. 1단계에서 세야 할 것은
"스캔 페이지가 몇 쪽인가"가 아니라 **"필드가 있는 스캔 페이지가 몇 쪽인가"** 다.
